# 2026-10-19 전체 로직 검토

## 핵심 경로

1. 배재대 포털 로그인 성공을 확인한 뒤 30분 유효한 앱 세션을 발급한다. 학교 비밀번호와 포털 쿠키는 저장하지 않는다. 최초 회원은 이름·닉네임·아바타를 직접 설정한다. 이름과 학번을 학교에서 가져오는 기능은 없다.
2. 학생은 학기별 시간표를 직접 입력한다. 학교 공개 공지는 수집·OCR 후 운영자가 원문을 검수할 수 있다. 날짜와 시간이 확정된 행사만 시간표와 비교한다.
3. 기관은 별도 관리자/직원 코드로 접속하여 공개 공지 후보를 검토하고 프로그램을 등록·공개·마감한다. 학생은 공개 프로그램에 신청하며 정원이 이미 수락 인원으로 찼다면 대기자로 접수된다.
4. 기관 담당자는 신청자를 수락·미선발·취소하고, 빈자리가 난 뒤 대기자를 수동으로 수락한다. 수락된 학생은 앱에서 참여 의사를 확인하거나 신청을 취소한다. 연락 시도는 담당자가 수동으로 기록한다.

## 검증 범위

- 분리된 임시 D1과 합성 학생 세션으로 **마감된 본인 신청의 조회·참여 확인**, 비신청자의 마감 프로그램 비노출, 마감 프로그램의 신규 신청 차단, 검수된 공지 일정의 기관 화면 반영을 HTTP API에서 확인했다. 실제 학생 계정이나 운영 신청 데이터는 시험에 사용하지 않았다.
- TypeScript 검사, 변경 파일 lint, 프로덕션 빌드, 학교 인증 단위 검사, 공지 파서 검사, 시간표 적합성 검사가 통과했다.
- 실제 학생과 기관 담당자가 서로 다른 기기에서 한 신청을 처리하는 현장 검증은 아직 수행하지 않았다.

## 남은 운영상 한계

1. 학교 로그인은 계정 성공만 확인한다. 기관에 표시되는 이름은 학생이 입력한 값이며 학교 확인 성명·학번이 아니다. 기관의 신원 확인이 필요한 업무에는 별도 절차가 필요하다.
2. 학생의 확인 필요 상태는 앱 안에만 표시된다. 푸시·문자·이메일 발송과 실제 참석 확인은 없다. 확인 기한이 지나도 자동 취소하지 않는다.
3. 기관 신청 명단 API는 프로그램당 최근 500건, CSV는 5,000건까지 처리한다. 규모가 커지면 페이지 조회와 내보내기 작업 분할이 필요하다.
4. 신청 상태 변경과 변경 이력 기록이 별도 DB 쓰기다. 이력 저장만 실패하면 상태는 바뀌었는데 API는 실패를 돌려줄 수 있다. 기관 파일럿 확대 전에 원자적 기록과 실패 복구를 보완해야 한다.
5. 공지 수집은 공개 페이지 구조와 OCR에 의존하며 자동 추출이 확정 정보는 아니다. 기관 화면의 후보 목록은 저장된 수집 결과이므로 새 공지의 즉시 반영을 보장하지 않는다.
6. Mac과 임시 Quick Tunnel 주소를 사용한다. 서버가 꺼지거나 터널 주소가 바뀌면 접속이 중단된다.
