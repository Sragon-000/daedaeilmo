# 10월 20일 기관·학생 파일럿 점검표

작성: 2026-10-19. 이 문서는 새 요청에 따른 구현·현장 검증 범위를 구분한다. 기존 기관 고객 전환 계획의 미검증 가설을 확인된 사실로 바꾸지 않는다.

## 이미 진행한 인터뷰에서 확인되는 범위

[5주차 최종 워크북](../7조_자료모음/최종문서/5주차_7조_워크북_최종본.docx)과 [학생 3명·기관 4명 응답 기록](../7조_자료모음/최종문서/7조_학생3명_기관4명_응답기록_최종본.docx)을 대조했다. 기록상 학생 5명·기관 5명을 인터뷰했다. 최초 학생 2명·기관 1명 기록과 추가 학생 3명·기관 4명의 **응답 정리문**은 기록 강도가 다르며, 후자의 면담 날짜·원본 메모·녹취는 제공되지 않았다.

- 기관 5명 모두 모집·관리의 추가 업무를 설명했지만, 같은 업무를 반복한 5명이라는 뜻은 아니다. 한 사례는 취소와 참여 의사 번복으로 인원 확정이 어려웠고, 다른 사례는 5명 취소 중 1명에게 답을 받지 못했다. 또 다른 사례는 대기자 충원 중 공유표 동시 수정으로 중복 안내를 했다. `연락두절`은 실제 사례로 볼 수 있으나 빈도·원인은 추가 대조가 필요하다.
- 학교 홈페이지·비교과 사이트·문자·학과 단체방 등 여러 경로에 홍보/안내한 사례가 있다. 그러나 **같은 공지를 우리 서비스에도 다시 등록해야 하는 부담**은 이 기존 기록에서 측정된 사실이 아니라 10월 19일 새로 전달된 문제 진술이다. 파일럿에서 실제 입력 횟수·수정 시간을 확인한다.
- 학생 5명 중 4명은 기존 경로에서 정보 확인이 어렵지 않거나 포스터가 편했다고 답했다. 한 학생은 마감 재확인 실패, 다른 학생은 내용의 진로 관련성이 낮아 미신청했다. 이는 새 앱의 **사용 의사**를 확인한 질문이나 행동 관찰이 아니다. 기존 인터뷰가 있었다는 사실과 새 기능의 수요 검증은 구분한다.

### 10월 19일 추가 기관 인터뷰에 대한 팀장 전달 내용

팀장이 별도로 진행한 기관 인터뷰의 핵심 불편을 **실제 학생의 신청 관리**라고 전달했다. 이는 기존 워크북의 5건과 구분되는 새 진술이다. 정확한 면담 날짜·기관 수·원본 기록·어느 신청 관리 단계가 가장 힘들었는지는 아직 받지 못했으므로, 여러 기관의 공통 문제나 정량적 빈도로 확대하지 않는다. 앞서 전달된 공지 중복 등록 부담도 별도 문제로 기록하되, 이번 파일럿의 중심 업무는 신청 접수 후 수락·취소·학생 확인 상태의 관리로 둔다. 공지 가져오기와 OCR은 등록 부담을 덜어 주는 보조 흐름이다.

이하 질문지는 인터뷰를 처음부터 다시 했다는 뜻이 아니라, 이미 수집한 응답으로 답할 수 없는 항목을 실제 화면을 보여 주며 추가 확인할 때 사용한다. 새 인터뷰의 원본 기록과 최근 실제 신청 처리 사례가 제공되면 단계별 우선순위를 갱신한다.

## 현재 구현한 운영 흐름

1. 기관 담당자는 별도 접속 코드로 `/institution`에 들어간다. 접속 뒤 등록된 프로그램이 있으면 신청 관리가 첫 화면이며, 신청 대기가 있는 프로그램을 먼저 보여 준다. 초기 관리자 코드는 Mac의 비공개 로컬 파일에 보관하며 학생 로그인과 분리한다. 관리자는 직원별 개인 코드를 발급하고 관리자·처리 담당자·조회 전용 권한을 설정하거나 코드를 회수할 수 있다. 현재 데이터 범위는 **배재대 한 기관 파일럿**이며 다기관 분리, 2단계 인증, 고정 주소는 없다.
2. 학교 홈페이지의 공개 공지 제목·본문을 가져오고, 포스터 이미지는 Apple Vision OCR로 일정 후보를 보완한다. 담당자가 제목·내용·대상·일시·정원·공결 근거를 검토한 뒤 초안을 공개한다. 공지 출처와 등록 내용은 분리하여 원문 갱신이 기관 수정 내용을 자동으로 덮지 않는다.
3. 배재대 학교 로그인에 성공하고 프로필을 설정한 학생은 이름·닉네임의 기관 제공에 동의한 뒤 공개된 프로그램에 신청한다. `신청 접수/대기 → 기관 수락/미선발 → 학생 수락 확인` 및 학생·기관 취소를 DB에 기록한다. 정원을 초과하면 대기 신청이 되고, 자리가 나도 담당자가 검토한 뒤 수락한다. 수락 시 학생 확인 기한이 부여되고 기관 화면에서 확인 대기·기한 경과·연락 시도 기록을 볼 수 있다. 기한 경과만으로 자동 취소하지 않는다. 학생은 앱 안에서 확인 필요 건수와 진행 상태를 볼 수 있다. **문자·이메일·푸시 발송이나 실제 참석 확인은 아직 없다.**
4. 기관의 처리 담당자와 관리자는 신청 명단 CSV를 내려받고, 관리자만 직원 코드를 발급·회수한다. 프로그램 변경·신청 처리·연락 기록에는 담당자 식별자가 남는다. 연락 기록은 실제 연락 수단과 결과를 수동 입력하는 기능으로, 앱이 연락을 대신 보내지는 않는다.
5. 학생이 직접 입력한 학기별 시간표와 행사 날짜·시간을 비교한다. 단일 일정이 확정되지 않으면 `일정 확인 필요`로 남긴다. `공결 가능`은 담당자가 확인 근거를 직접 기재했을 때만 붙고, 실제 수업의 공결 인정은 수업 담당자가 결정한다.

## 인적 정보의 정확한 범위

학교 로그인이 증명하는 것은 **배재대 계정 로그인 성공**이다. 현재 학교 포털에서 성명·학번을 신뢰할 수 있게 반환하는 공식 API/SSO 계약이나 검증된 조회 경로가 없다. `members.name`은 학생이 직접 입력한 값이며 기관 화면에도 그렇게 표시한다. 학번 원문은 현재 저장·전달하지 않는다. 학교 인증을 통해 확인한 성명·학번으로 자동 기입한다는 요구는 **미구현**이다. 이 값이 필수인 실제 기관 업무에 현재 화면을 신원 확인 수단으로 쓰지 않는다.

## 내일 현장 확인할 항목

- 기관 책임자가 접속 코드의 사용 범위와 파일럿 프로그램 등록을 허용했는지 기록한다. 실제 학생 명단을 다루기 전에 보관 기간, 취소·삭제, 사고 연락처와 백업 복원 책임자를 정한다.
- 실제 담당자가 학교 공지 하나를 선택해 초안으로 가져와 수정·공개한다. 같은 내용의 중복 입력 시간과 원문 대조 시간을 측정한다.
- 학생 본인이 학교 로그인 후 수동 시간표를 입력하고, 프로그램 신청·상태 확인·수락 확인·취소를 수행한다. 기관 화면의 신청 수와 상태를 대조한다.
- 기관 담당자가 최근 실제 신청 처리 사례 한 건을 따라 접수 확인부터 수락/미선발·취소·학생 확인까지 처리한다. 기존 방식과 비교해 확인에 걸린 시간, 누락·중복 처리, 연락이 필요한 지점을 기록한다. 현재 앱에는 학생에게 결과를 자동 발송하는 기능이 없으므로, 연락두절 해결을 검증했다고 말하지 않는다.
- 학교 성명·학번 자동 조회는 공식 연동 문서 또는 포털의 명시적 제공 경로를 확보한 뒤 재평가한다. 지금은 직접 입력 이름을 학교 확인 정보로 제시하지 않는다.
- 임시 Mac/Quick Tunnel은 운영 호스팅의 가용성 보장이 없다. 직원별 코드와 권한 회수는 마련했지만, 외부 현장 사용 전에 고정 주소, 모니터링, 백업 복구와 다기관 분리 기준을 확인한다.

## 학생 인터뷰 기록지 (실제 응답만 기록)

참여자 코드, 날짜, 학년/소속 범위, 개인정보 기록 동의 여부를 먼저 적는다. 이름·학번·비밀번호를 인터뷰 기록지에 넣지 않는다.

1. 최근 실제로 신청한 교내 프로그램을 어떤 경로로 발견했나요? 공지 제목만 봤을 때 내용을 알아보는 데 몇 단계가 걸렸나요?
2. 모집 요건·일시·장소·신청 마감을 한 카드에서 볼 수 있다면 무엇을 먼저 확인하나요? 정보가 틀리면 어떤 문제가 생기나요?
3. 본인의 시간표를 직접 입력해 여유 시간을 찾는 방식이 쓸 만한가요? 입력하는 데 걸린 시간과 수정 빈도는?
4. 신청 후 기관 수락·취소 현황과 확인 버튼을 실제로 사용할 의사가 있나요? 어느 순간에 알림이 필요하고, 받지 못하면 어떻게 확인하나요?
5. 공결 가능 표시를 믿으려면 어떤 기관·수업의 근거가 보여야 하나요? 실제 공결 신청 절차는 무엇인가요?
6. 학교 로그인과 신청 정보 제공 범위를 설명한 뒤, 신청을 중단하게 만드는 정보 요구가 있는지 묻는다.

인터뷰 결과 표: `참여자 코드 | 실제 사용 사례 | 관찰한 행동 | 직접 인용(동의 시) | 문제의 강도 | 대안/기존 도구 | 다음 행동`. **인터뷰 계획을 이용 의사나 검증 완료로 계산하지 않는다.**

## 기관 인터뷰 기록지 (실제 응답만 기록)

최근 진행한 프로그램 한 건을 기준으로 학교 공지 게시→학생 신청 접수→선발→연락→취소/대기 충원까지 실제 도구와 작업 시간을 따라간다.

1. 학교 공지를 올린 뒤 어떤 채널에 같은 내용을 다시 입력하나요? 최근 한 건의 입력·수정 횟수와 소요 시간은?
2. 연락이 닿지 않았던 신청자는 최근 몇 건이었고, 어느 상태에서 멈췄나요? 현재 어떤 방식으로 확인·대체하나요?
3. 담당자에게 필요한 상태는 신청, 수락, 학생 확인, 취소, 대기 중 어디까지인가요? 현 시스템에서 누가 최종 상태를 결정하나요?
4. 학교 원문을 가져온 뒤 어떤 항목을 사람이 검수해야 하나요? OCR 오독이나 원문 수정이 발생하면 누가 정정하나요?
5. 공결 가능 여부를 누가 판단하고, 어떤 문서·범위·수업에서 유효한가요?
6. 실제 자료를 외부 파일럿에 사용할 권한자는 누구인가요? 직원 접근, 보관·삭제, 사고 대응과 학교 IT 검토 조건은?
7. 현재 업무와 이 화면을 같은 사례로 비교했을 때 줄어든 시간과 새로 생긴 입력 시간은 각각 얼마인가요? 다음 시연·자료 검토·내부 승인 중 어떤 행동이 가능한가요?

인터뷰 결과 표: `기관/역할 | 최근 프로그램 | 기존 작업·시간 | 연락두절 사례 | 중복 입력 사례 | 자료 사용 권한 | 실제 후속 행동`. 담당자 발언만으로 공식 기관 승인이나 구매 의사를 추정하지 않는다.
