# 대대일모 MVP 실험 실행 계획

> 2026-10-12 방향 변경: 현재 우선순위는 학생 행동 실험이 아니라 **프로그램을 보여 주는 모바일 미리보기**다. 초대·동의·클릭 지표 수집은 공개 경로에서 중지했다. `/preview`는 학교 로그인 없이 실제 검수 공지 4건과 시간표·리뷰·프로필 흐름을 보여 준다. 시간표 조작은 브라우저 안의 시연이며 리뷰는 계획 중인 화면으로 표시한다. 아래 문서는 실험을 다시 결정할 때 참고할 과거 계획이다.

작성일: 2026-10-12

## 결론과 범위

현재 코드는 배재대 로그인, 실제 공지 수집, 수동 시간표, 행사 비교, 원문 이동, 저장과 관리자 검수를 갖춘 **작동형 프로토타입**이다. 이번 MVP는 기능을 더 붙이는 일이 아니라, 학생이 실제 행사 후보를 보고 학교 원문에서 신청 정보를 확인하는지 시험할 수 있는 최소 흐름을 완성하는 일이다.

첫 고객은 배재대 비교과 활동에 관심 있는 학생이다. 실험 가정은 “공강에 맞는 검수된 실제 활동을 한곳에서 보면 학생이 자발적으로 학교 원문을 연다”이다. 6주차 팀 문서의 잠정 판정선은 **2주 동안 학생 10명 중 4명 이상이 자발적으로 원문에 이동**하는 것이다. 클릭 반복은 같은 학생 한 명으로 세며, 신청과 실제 참여는 별도로 기록한다. 이 수치는 시장에서 입증된 기준이 아니라 이번 팀 실험의 판단 규칙이다.

MVP 형태는 기존 모바일 웹을 재사용한 **초대 링크 기반 실험 화면 + 수동 행사 검수·관찰**이다. 학교 계정이 필요한 본 앱은 유지한다. 실험 화면은 학교 비밀번호·실명·학번을 받지 않고 공개 공지 정보만 보여 준다. 과거의 “외부인 사용 제한” 요구를 지키기 위해 참여자별 임의 초대 링크를 사용하고, 회원 API·관리자 화면·개인 데이터와 분리한다. 초대 링크가 유출돼도 학교 계정이나 회원 기록에 접근할 수 없어야 한다.

## 순서와 완료 조건

### 1. 실험용 행사 공급 확정

- 공식 배재대 공지에서 최근 후보 20건을 뽑아 원문과 제목, 행사일·시간, 신청 마감, 장소, 대상, 원문 링크를 대조한다. 빠진 행사와 중복·지난 행사도 기록한다.
- 기존 Mac 관리자 화면에서 검수한 후보만 실험 목록에 노출한다. 원문이 바뀌어 검수가 해제되면 실험 목록도 자동으로 바뀌어야 한다.
- 유효한 후보가 부족한 날을 실험 실패에서 제외하지 않고 **공급 부족**으로 기록한다. 검수 작업 시간도 기록한다.

**완료 조건:** 표시된 카드마다 학교 원문 링크와 최근 확인 시각이 있고, 종료·모호한 일정은 여유 행사로 표현되지 않는다. 테스트할 수 있는 후보의 수와 부족 사례를 보고할 수 있다.

### 2. 두 화면의 초대 링크 기반 실험 경로 구현

- 새 경로에서 참여자별 임의 초대 링크를 확인한다. 초대 ID와 실명·학번의 대응표는 앱 DB에 넣지 않는다.
- 첫 화면은 요일·시작·끝 등 가능한 시간만 받는다. 다음 화면은 검수된 행사 카드의 제목, 일정, 장소, 대상, 신청 정보, 출처와 **학교 원문 보기**를 보여 준다.
- 기존 `lib/campus-events.ts`의 날짜·마감 판정 원칙을 참고하되, 수업 충돌을 계산하는 `assessEvent()`는 공강 구간에 직접 적용하지 않는다. 공강 입력용 판정을 별도 순수 함수로 만들고, `app/campus-events.tsx`의 카드 표현을 필요한 부분만 재사용하되 학교 인증 API에 의존하지 않게 분리한다.
- 실험 API는 `campus_events` 중 확인된 공개 공지의 허용 필드만 읽는다. 기존 `/api/events`, `/api/event-saves`, `/api/event-opens`의 인증을 해제하지 않는다. 초대 링크로 회원·시간표·리뷰·관리자 데이터에 접근할 수 없어야 한다.
- 실험 화면에는 프로필, 전체 시간표, 리뷰, OCR 확장, 알림, 결제, 신청 대행을 넣지 않는다. 저장은 2순위이며 없어도 원문 이동 실험을 진행한다.

**완료 조건:** 학교 계정이 없는 테스트 폰에서도 유효한 초대 링크로 `가능 시간 → 행사 목록 → 학교 원문`을 끝까지 진행한다. 잘못되거나 만료된 링크는 실험 데이터를 보여 주지 않는다.

### 3. 측정과 접속 검증

- 참여자 식별자는 U01~U10으로 표시한다. 기록할 최소 항목은 사용 동의, 시작 여부, 가능한 시간 입력 완료, 검수 행사 노출, 자발적 원문 이동 시도, 실제 학교 원문 열림, 실패 이유와 날짜다. 한 사람의 반복 클릭은 판정에서 한 번만 센다.
- 앱 로그는 클릭 **시도**만 증명하므로, 실제 원문 페이지가 열린 것은 대면 관찰 또는 사용 후 확인으로 별도 검증한다. 개인정보가 필요 없는 집계표를 사용한다.
- Mac 서버 재시작과 HTTPS 링크 변경 시 대처 절차를 적는다. 2주간 자발적 재방문을 볼 예정이라면 같은 주소를 유지할 수 있는 터널을 우선 마련한다. 임시 주소만 쓸 경우 링크 재발급과 접속 중단 시간을 반드시 기록한다.
- 로그아웃·시크릿 브라우저의 iOS와 Android, 다른 Wi-Fi 및 이동통신망에서 초대 링크, 카드, 원문 열림을 점검한다. 관리자 경로와 회원 API 접근은 계속 차단한다.

**완료 조건:** 팀 밖 테스트 폰에서 전 과정을 재현하고, 누가 언제 원문을 열었는지 중복 없이 판정할 수 있으며, 접속 실패도 기록할 수 있다. 여기까지가 **실험 가능한 MVP 완성**이다.

### 4. 학생 10명·2주 실험

- 기관 관계자는 학생 10명의 분모에 넣지 않는다. 최근 비교과 탐색 경험, 활동 관심, 신청·미신청 경험이 다른 학생을 섞어 모집한다. 참여 동의를 확인하고 U01~U10을 배정한다.
- 참가자가 최근 활동을 찾았던 방법을 먼저 듣고, 초대 링크를 제공한다. “원문을 눌러 보라”고 지시하지 않는다. 사용 후 원문으로 이동하거나 이동하지 않은 이유, 찾을 만한 활동이 없었는지, 일정 충돌인지, 관심·자격 문제인지를 나눠 기록한다.
- 2주 후 자발적 원문 이동을 학생 단위로 집계한다. **4/10 이상이면** 다음 소규모 반복 실험으로 진행, **2/10 이하이면** 문제·공급·화면 중 주된 원인 하나를 바꿔 재시험, **3/10이면** 판단을 보류한다. 10명 미완료 또는 유효 행사 부족이면 결과를 성공·실패로 단정하지 않는다.
- 원문 클릭률은 신청률이나 실제 참여율로 표현하지 않는다. 결과표에 성공 사례와 실패 사례, 공급 부족, 운영자가 쓴 시간을 함께 남긴다.

**완료 조건:** 학생 10명의 분모, 각자의 실제 행동, 원문 이동 여부와 이유, 2주 운영 부담을 근거로 다음 반복·수정·중단 결정을 내린다. 이때부터 **학생 가치 가설을 평가한 MVP**라고 설명할 수 있다.

## 일정과 우선순위

준비 작업은 팀의 가용 인력에 따라 약 1주, 사용 실험은 2주로 잡는다. 순서는 `행사 20건 검수 → 초대 링크 기반 두 화면 → 접속·기록 검증 → 학생 10명 실험 → 결과 판정`이다. 준비 중 모집을 병행하되, 검수된 후보와 정상 접속 링크가 준비되기 전에는 실험 시작일을 확정하지 않는다.

본 앱의 학교 로그인과 회원 기능은 이번 실험 때문에 제거하지 않는다. 계명대 연동, iOS·Android 네이티브 앱, 기관 유료 상품, 실제 공간 리뷰, 자동 알림은 학생의 원문 확인 행동이 확인된 뒤 우선순위를 다시 정한다. 기관 인터뷰는 학생 실험과 별도로 계속하되, 기관 의견만으로 학생 사용성을 검증했다고 보지 않는다.
