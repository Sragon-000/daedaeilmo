# 10월 20일 기관 신청 관리 파일럿 개발·검증 계획

작성: 2026-10-19. 목표는 **실제 학생의 신청을 기관 담당자가 접수·처리하고 학생이 결과를 확인하는 한 건의 흐름**을 10월 20일까지 끝까지 검증하는 것이다. 추가 기관 인터뷰의 핵심 불편은 팀장이 `실제 학생 신청 관리`라고 전달했다. 어느 처리 단계가 가장 어려운지, 기관 수와 면담 원본은 아직 확인되지 않았으므로 이 계획의 우선순위는 파일럿 가설이다. [인터뷰 근거와 현재 범위](./2026-10-20-institution-pilot.md)를 함께 본다.

## 우선순위와 작업 순서

### P0 — 오늘 구현·검증

1. **실제 신청의 정확성:** 학생 1명·기관 담당자 1명이 허용한 프로그램 1건으로 `공개 → 신청 → 기관 수락 → 학생 확인`을 수행하고, 미선발·학생 취소·기관 취소는 별도 분기로 시험한다. 학생/기관 화면의 동일한 상태, 대기·수락·정원 수, 새로고침 후 유지 여부를 확인한다. 중복 신청·중복 클릭·정원 초과·권한 없는 조회/수정·다른 프로그램 접근을 함께 시험한다. 발견된 결함은 이 흐름부터 수정한다.
2. **기관의 처리 대기열:** 프로그램별 신청 대기, 수락 후 학생 확인 대기를 한눈에 볼 수 있도록 집계·정렬/필터를 보완한다. 처리 후 숫자가 즉시 갱신되게 하고, 학생이 앱에 다시 들어오지 않으면 `확인 대기`로 남는다는 점을 명확히 보여 준다. 연락 발송이 없는 상태를 `연락 완료`로 해석하지 않는다.
3. **학생 신청 화면:** 신청 전 기관에 전달되는 이름·닉네임이 직접 입력한 값임을 다시 확인하고, 신청 결과·현재 상태·취소 가능 여부를 실제 휴대폰에서 확인한다. 신청 버튼 연속 입력과 서버 오류 때 성공처럼 보이지 않는지 점검한다.
4. **실제 행사 정보:** 기관 담당자가 공개 공지/포스터와 프로그램의 모집 조건·일시·장소·정원·공결 근거를 대조해 **검수한 1건**만 공개한다. OCR 결과와 원문이 다르면 담당자 확인값을 사용한다. 날짜·시간이 모호하면 시간표 추천 확정 표시를 하지 않는다.
5. **운영 안전성:** 변경 전 D1 백업, 복원 방법 확인, 기관 코드/학생 세션 접근 차단, 공개 HTTPS 주소와 서버 상태를 점검한다. Mac 재시작으로 주소가 바뀌면 시연 참가자에게 새 주소를 전달한다. 비밀번호·접속 코드·신청자 명단을 발표 자료나 Git에 넣지 않는다.

### P1 — 10월 20일 현장 검증

1. 기관 담당자가 **최근 실제 신청 관리 사례**와 현재 화면을 비교한다. 접수 확인, 선발, 연락, 취소, 학생 확인 중 어디가 가장 오래 걸리는지와 기존 도구를 기록한다. 앱에서 줄어든 시간과 새로 생긴 입력 시간을 모두 측정한다.
2. 학생이 본인 휴대폰에서 발견→신청→결과 확인을 수행한다. 사용 의사라는 답변과 실제 행동을 구분해 기록한다. 추가 인터뷰의 날짜·역할·원문 메모를 제공받으면 기존 5주차 응답과 구분해 정리한다.
3. 실제 운영 책임자와 프로그램 게시·학생 정보 처리 허용 범위, 보관·삭제 담당자, 장애 연락처를 확인한다. 허용 범위가 정해지지 않았다면 실제 명단 확대를 멈추고 제한된 검증 결과로만 발표한다.

## 10월 20일 완료 판정

- 배재대 계정으로 로그인한 학생의 신청 1건이 기관 화면에 **정확히 한 번** 나타난다. 기관 처리가 학생 화면에 반영되고, 양쪽 새로고침 후에도 상태가 일치한다.
- 수락 정원을 넘길 수 없고, 다른 학생·무인증 사용자가 신청자 명단이나 처리 API에 접근할 수 없다. 취소와 재신청에서 건수·상태가 어긋나지 않는다.
- 다른 학생의 소유권 검증에는 동의한 **두 번째 배재대 계정**이 필요하다. 참여 계정이 없으면 이 항목은 미검증으로 남기고 완료 처리하지 않는다.
- 기관은 신청 대기와 학생 확인 대기를 구분해 찾는다. 다만 학생이 확인하지 않은 사유나 실제 연락 가능 여부는 앱만으로 알 수 없음을 표시한다.
- 실제 공지와 대조한 프로그램 한 건에서 시간표 적합/충돌/판정 불가와 공결 표시의 근거를 설명할 수 있다.
- 개발 결과와 별개로 인터뷰 발언·관찰, 기관의 데이터 사용 허용 여부, 미완료 항목을 분리해 제출한다.

## 내일 완료로 약속하지 않는 항목

- **학교 확인 성명·학번 자동 수집:** 포털 로그인 성공만 확인된 상태다. 공식 API/SSO 또는 검증 가능한 조회 경로와 사용 승인이 필요하다. 현재 직접 입력 이름을 학교가 확인한 값으로 바꾸어 표시하지 않는다.
- 기관이 학교 확인 학번·성명을 신청 처리의 필수 조건으로 요구한다면, 그 값을 제공할 수 있기 전까지 해당 업무를 **실제 신원 확인 완료**로 운영하지 않는다. 기관의 기존 확인 절차를 유지하며 파일럿 범위를 다시 정한다.
- **연락두절 해결:** 푸시·문자·이메일 알림과 실제 참석 확인은 없다. 앱 내 확인 대기 표시까지만 검증한다.
- **상시 운영 서비스:** 직원별 개인 코드와 회수는 구현했지만, 한 기관 범위의 초기 관리자 코드, 임시 주소, Mac 의존성으로는 다기관 분리·고정 주소·장애 복구를 충족하지 못한다. 내일의 결과는 허용된 범위의 실제 데이터 파일럿과 그 검증 결과다.
- 계명대 연동, 다른 대학 확장, 리뷰 확장, OCR 자동 확정은 이번 납품 범위 밖이다.

## 작업 기록 양식

`시각 | 역할(학생/기관) | 프로그램 코드 | 수행 단계 | 기대 상태 | 실제 상태 | 소요 시간 | 오류·재작업 | 근거/스크린샷 위치`. 개인정보가 드러나는 이름·학번·비밀번호는 기록하지 않는다. 오류는 재현 절차와 수정 후 재검증 결과를 남긴다.

## 10월 19일 확장 구현 기록

기관 인터뷰의 신청 관리 문제에 맞춰 신청 상태 필터·학생 진행 단계·수락 후 확인 기한·실제 연락 시도 기록·대기자 수동 충원·개인 담당자 코드와 권한 회수·변경 이력·CSV를 추가했다. 학생의 `확인 필요`는 앱 안에서만 표시하며 외부 메시지를 보내지 않는다. 새 DB 스키마 적용 전 Mac 로컬 D1을 백업했고 무결성 검사가 통과했다.

실제 자료와 분리된 임시 D1에서 합성 학생 세션으로 중복 신청, 정원 초과 대기 등록, 빈자리 발생 후 담당자 수락, 학생 확인, 연락 기록, 권한별 API 차단, 담당자 세션 회수, CSV 수식 주입 방지를 검증했다. 공개 HTTPS 경로의 비인증 기관 API도 401로 차단된다. **실제 학생·기관 담당자의 두 기기 현장 사용과 외부 알림 전달은 아직 검증하지 않았다.** 학교 확인 성명·학번과 상시 운영 조건도 여전히 미완료다.
