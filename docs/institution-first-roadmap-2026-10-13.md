# 대대일모 기관 고객 전환 계획

작성일: 2026-10-13. 재검토일: 2026-10-13. 근거 범위는 1~6주차 최종 문서, 기관 인터뷰와 현재 구현이다. 이는 **기관 고객을 우선 탐색하는 방향 제안**이며 확정된 구매자·공통 문제·제품 요건이 아니다. 과거 학생 중심 실험이나 기관 유료 구매가 이미 검증된 것으로 해석하지 않는다.

## 재검토 결론

기관을 고객 후보로 두는 방향은 유지하되, 첫 제품은 **한 운영 팀의 한 반복 업무**가 확인된 뒤 결정한다. 이전 안의 `집계 자료로 취소·대기 업무를 처리한다`는 흐름은 성립하지 않는다. 집계 자료는 현황 보고만 가능하고, 개별 처리 대기열에는 건별 식별자와 변경 이력이 필요하다. 또한 회상으로 답한 업무 시간과 서로 다른 프로그램 2건만으로 `25% 절감`을 입증할 수 없다. 이 수치는 출처가 있는 구매 기준이 아니므로 통과 조건에서 뺀다. 실제 데이터 사용과 직원용 로그인·배포는 기관 승인과 운영 준비를 별도 통과 조건으로 둔다.

## 결정할 고객과 문제

첫 디자인 파트너 후보는 **배재대학교의 비교과 프로그램 운영 팀 한 곳**이다. 창업·학과 운영 팀까지 한 고객군으로 묶지 않고, 같은 절차를 쓰는지 확인한 뒤 확장한다. 실사용자는 프로그램 담당자, 도입 후원자와 예산·구매 결정자는 확인해야 할 별도 역할이다. 학생은 기관 프로그램의 수혜자이지 이 단계의 구매자가 아니다. 실제 팀·결재권자·예산 경로는 아직 확인되지 않았다. 다른 대학과 외부 기관은 첫 파일럿 범위에서 제외한다.

잠정 문제는 “프로그램마다 신청·취소·확정·대기·참석 상태를 여러 도구에서 대조하며 반복 연락과 수작업을 한다”이다. 이는 아직 서로 다른 업무를 묶은 가설이다. 제품 가치 가설은 **한 가지 상태 대조·후속 처리 업무에 드는 담당자 시간을 줄인다**로 제한한다. 모집 인원 증가, 신청 완료, 실제 참여 증가, 유료 구매는 별도 검증 결과다.

우선 확인할 업무 후보는 **신청 이후 취소·대기자 충원**이다. 인터뷰 5건에서 이 업무의 빈도·소요 시간·현재 도구가 같은 방식으로 반복된다는 증거는 아직 없다. 추가 확인에서 반복되지 않으면 같은 기관 고객 안에서 홍보 연장 또는 출석·수료 대조 중 하나를 다시 선택한다. 이 시점에는 담당자용 기능 목록을 고정하지 않는다.

## 제품의 중심 흐름과 재사용 범위

기관용 경로는 조사에서 선택된 **한 업무**에만 맞춘다. 학교 신청·출석 시스템을 대체한다는 전제는 두지 않는다. 자료 사용은 두 경로로 구분한다.

- **집계만 있는 시연:** 프로그램별 수치, 기준 시각, 출처를 입력해 현황을 보여 준다. 개별 신청 건을 구분할 수 없으므로 취소·대기자 충원 대기열이나 개인별 업무 완료 판정은 만들지 않는다.
- **건별 업무 파일럿:** 실제로 건별 처리가 필요하고 기관이 자료 제공·사용을 승인한 경우에만 기관이 발급한 가명 코드와 상태 변경 이력을 받는다. 코드와 실명·연락처의 대응표는 기관 내부에 둔다. 가명 코드도 개인별 상태를 추적하는 자료이므로 접근 권한, 보관 기간, 삭제, 오류 정정 책임을 정한 뒤 사용한다. 연락 발송·최종 선발·출석 판정은 기관의 기존 승인 절차에서 수행한다.

공식 공지는 출처 URL과 수집 시각을 유지하고, 기관 담당자가 확인·수정한 필드는 별도로 표시한다. 원문 변경이 담당자 수정 내용을 조용히 덮거나, 수집 정보가 기관의 공식 확정 데이터처럼 보이게 하지 않는다. 학생용 공지 갱신은 기관이 그 업무를 원할 때만 별도 범위로 추가한다.

현재 코드는 학생 로그인·수동 시간표, 공식 공지 수집·검수, 행사 카드/원문 링크, 학생별 저장·원문 열기 **시도** 기록, 로그인 없는 시연 화면과 Mac 로컬 관리자 화면을 갖췄다. 공개 공지와 검수 기능은 학생에게 보여 주는 경로로 재사용할 수 있다. 반면 `campus_events`에는 기관 소유자·운영 단계·목표/신청/확정/참석/수료 수치가 없고 Mac 관리자 화면은 127.0.0.1 전용이다. 기관 담당자 제품으로 그대로 개방해서는 안 된다. 원문 클릭만으로 신청 또는 출석을 알 수도 없다.

| 유지·재사용 | 새로 필요 | 이번 범위에서 보류 |
| --- | --- | --- |
| 배재대 공개 공지, 원문·포스터, 검수 상태, 출처 변경 시 검수 해제, 학생용 공개 시연 | 선택한 한 업무에 필요한 프로그램 소유권, 담당자 인증·권한, 상태·변경 이력, 측정 기록. 건별 대기열과 가명 CSV는 기관 승인과 업무 검증을 통과했을 때만 | 다른 대학 SSO, 학생 신청 대행·결제, 푸시 발송, 네이티브 앱, 리뷰·아바타 확장, OCR 확대, 학생용 공지 발행 자동화 |

학생 앱은 유지하되 신규 개발 우선순위에서 내린다. 학생 화면은 기존 서비스와 공개 시연에 활용한다. 기관이 실제로 공지 발행을 요청하기 전에는 기관용 최소 제품의 필수 기능으로 묶지 않는다. 공강 비교는 기관 가치의 핵심 지표가 아니다.

## 도입·수익 가설도 별도로 검증

초기 접점은 기존 기관 인터뷰 대상과 배재대 프로그램 운영 팀이다. 첫 제안은 판매가 아니라 **가상·집계 자료로 업무를 함께 검토하는 시연**이다. 실제 기관 자료를 쓰는 파일럿에는 업무 책임자와 데이터 제공 권한자의 승인 범위, 학교 IT·보안 검토 필요 여부, 보관·삭제 조건을 먼저 문서화한다. 담당자가 편하다고 말하는 것과 부서가 비용을 지불하는 것은 다르므로, 예산·구매 결정자를 확인하고 기존 도구 비용·외부 업체 검토 경험·예산 편성 시기·구매 단위를 묻는다. **실제 다음 단계 행동**인 추가 회의, 자료 검토 허용, 파일럿 승인, 견적 요청 또는 내부 검토 요청을 단계별로 따로 기록한다. 가격은 그 전까지 정하지 않는다.

수익 후보는 기관의 프로그램 운영 지원비이지만 현재는 가설이다. 4~5주차 문서의 정보 관리 주 3시간·서버/알림 월 5만 원도 측정값이 아니다. 파일럿에서는 `프로그램당 수집·검수 시간 + 데이터 정리 시간 + 고객 지원 시간 + 호스팅 비용`을 기록해 실제 운영 원가를 계산한다. 기관이 절감한 시간만큼 팀의 수작업이 늘면 자동화/가격 구조를 다시 설계한다.

## 단계별 실행과 통과 조건

단계는 주차보다 **증거와 승인**으로 넘어간다. 인터뷰 일정, 기관 검토, 실제 프로그램 개최 간격을 확인하기 전에는 `1주+1주+2주`를 납기로 약속하지 않는다. 아래 숫자는 조사 설계용 최소 표본이며 시장 검증이나 통계적 대표성을 뜻하지 않는다.

| 단계 | 결과물 | 통과 조건 |
| --- | --- | --- |
| A. 문제·권한 확인 | 기존 응답자 재접촉과 가능하면 신규 운영자 면담. 최근 프로그램의 실제 작업 흐름, 기존 폼·시트·학교 시스템, 작업 건수·반복 주기, 불편이 없었던 사례도 확인. 담당자·업무 책임자·데이터 제공 권한자·예산 결정자 구분. 기관이 보여 줄 수 있는 자료는 사전 허용 범위 안에서만 확인. | 같은 종류의 팀 최소 2곳에서 **동일한 업무 단계**와 실제 자료 양식이 확인되고, 한 팀의 책임자가 후속 시연에 참여한다. 이것은 문제 후보 선별이지 제품 효과·구매 검증이 아니다. 맞지 않으면 하위집단 또는 업무를 다시 선택한다. |
| B. 수동 시연·기준선 설계 | 선택한 한 업무의 화면/시트로 담당자와 함께 시뮬레이션. 집계 자료라면 현황 보고만, 가상 건별 자료라면 대기열 시연만 수행. 기존 방식에서 담당자가 하는 입력·대조·연락·정정 단계와 팀이 대신한 수작업을 각각 기록. | 담당자가 실제 업무와 다른 부분을 지적할 수 있고, 기준선의 작업 단위·기록 방법에 동의한다. 후속 파일럿 담당자·데이터 범위·학교 검토 경로가 지정된다. 팀 대행 시간이 길면 제품화 전에 입력 경로를 재설계한다. |
| C. 한 업무의 최소 제품 | A·B에서 정해진 업무만 구현. 집계형이면 프로그램 현황·출처·기준 시각·정정 이력, 건별형이면 승인된 가명 코드·상태 전이·처리 대기·변경 이력 중 필요한 것만 구현. 직원 인증, 프로그램별 접근 제어, 내보내기/삭제, 오류 복구는 실제 자료 사용 전에 준비. 학생용 발행과 일곱 가지 상태 전부는 기본 범위가 아니다. | 담당자가 자기 범위의 한 업무를 처음부터 끝까지 처리하고 기존 원본과 대조한다. 무권한·다른 프로그램 접근 차단, 중복·누락·잘못된 상태 변경의 복구, 삭제·백업 복원이 확인된다. 실제 자료 사용은 별도 승인·배포 조건을 충족해야 한다. |
| D. 제한된 현장 파일럿 | 승인된 한 운영 팀에서 실제 프로그램에 사용. 첫 회차는 안전성과 업무 적합성을 관찰하고, 비교 가능한 다음 회차가 있을 때 재측정한다. 담당자 기존 작업 시간, 도구 추가 입력·대조 시간, 오류·정정, 팀 지원 시간, 이용 중단/복귀 사례를 모두 기록. | 상태 정확성과 업무 완료를 확인하고, 담당자 **순절감 시간**과 팀 지원 비용을 보고한다. 담당자와 도입 책임자가 파일럿 전에 합의한 최소 유용 효과와 비용을 비교한다. 비교 가능 자료가 없으면 절감률을 주장하지 않는다. 오류 증가, 추가 입력 부담, 승인 범위 이탈은 중단·재설계 조건이다. 재사용 의사와 구매 검토는 별개로 확인한다. |

한 단계의 미달을 다른 지표로 덮지 않는다. 공통 업무가 없다면 비교과 전반 대신 과정이 비슷한 운영 팀으로 다시 좁힌다. 시연이 작업을 늘리면 자동화보다 입력 절차부터 바꾼다. 도입 승인·자료 제공이 없다면 공개 자료와 **가상 예제**로만 시연한다. 기관 자료의 집계도 그 기관이 제공·사용을 허용했는지 먼저 확인한다.

### 측정 규칙

선택한 업무의 `한 건`(예: 취소 1건 처리)을 먼저 정의하고, 입력 준비→상태 대조→후속 연락/처리→정정까지 같은 범위로 잰다. 각 회차에 담당자가 직접 기록한 시작·종료 시간, 처리 건수, 오류·재작업 건수, 도구 때문에 새로 생긴 입력 시간을 남긴다. **담당자 순절감**은 `기존 방식의 같은 업무 시간 − 도구 사용 시 업무 시간(추가 입력·대조 포함)`으로 계산하고, 팀이 대신한 정리·지원 시간은 별도 원가로 공개한다. 회상 수치는 참고만 하며 기준선으로 쓰지 않는다. 기존 방식과 제품을 동시에 중복 수행한 회차는 안전성 검토에는 쓰되 절감률 비교에서는 별도로 표시한다. 프로그램 규모·업무량·담당자가 달라지면 단순 총시간 비교를 피하고 `건당 시간`과 총시간을 함께 보고한다. 소수 사례의 결과는 해당 팀·프로그램의 관찰값으로만 설명한다.

## 기술·운영 선행 조건

1. 기존 학생 `members`와 기관 계정을 분리한다. 자료 형태가 정해지면 `organizations`, `staff_memberships`, `programs`, 집계 스냅샷 또는 건별 상태 이력, `audit_log` 중 필요한 구조만 설계한다. 모든 기관 API에서 로그인뿐 아니라 프로그램 소유 범위를 서버에서 검사한다. DB 변경 전 백업과 복구 시험을 한다.
2. 현재 Mac 관리자 토큰과 학생 포털 계정은 기관 직원 로그인에 재사용하지 않는다. 담당자 초대·권한 회수, 세션 관리, 기관이 허용한 직원 인증을 설계한다. 학교 시스템의 학생 계정 성공 판정은 직원 자격이나 기관 데이터 접근 권한의 증거가 아니다.
3. 현 Mac의 `wrangler dev`와 임시 Quick Tunnel은 화면 시연용이다. [Cloudflare 공식 문서](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)도 Quick Tunnel을 테스트·개발용으로 규정한다. 실제 기관 자료를 원격으로 처리하기 전에 배포 환경, 고정 주소, 직원 접근 통제, 감사 기록, 장애 알림, 백업·복구 시험, 운영 책임자와 중단·삭제 절차를 갖춘다. 기관 API를 현재 공개 프록시에 바로 추가하지 않는다.
4. 자료 계약에는 **원천 시스템/제공자, 제공일·기준 시각, 상태 정의, 고유 인원과 회차 연인원 구분, 중복·취소·재신청 처리, 정정 권한**을 명시한다. 원문 열기 **시도**, 신청, 확정, 참석, 수료는 서로 다른 수치다. 공식 연동이 없으면 학교에서 받은 집계의 기준 시각을 표시하고 자동 수집·OCR 결과를 확정 자료로 승격하지 않는다.

첫 기관에서 한 업무의 정확성, 담당자 순절감, 반복 사용, 기관의 후속 행동이 확인된 뒤에만 다른 부서로 복제한다. 다른 대학으로 확장할 때는 공지 구조·자료 제공 범위·직원 인증을 학교마다 따로 확인한다. 배재대 학생 포털 로그인 구현만으로 다른 학교나 기관의 공식 연동을 약속하지 않는다.

## 문서와 발표 정리

역사 기록인 1~6주차 워크북의 당시 선택과 인터뷰를 새 방향에 맞춰 소급 수정하지 않는다. 새 린 캔버스에는 **기관 고객/담당자/결재권자**, 반복 업무, 기존 시트·폼·학교 시스템, 예상 절감 시간, 도입 장벽과 비용 가설을 적는다. 학생 `4/10 원문 이동`은 과거 B안 판정선으로 남기고 기관 파일럿 기준표를 별도로 만든다. 발표는 “학생이 공지를 못 찾는다”보다 “기관이 프로그램 운영 상태를 변경·대조할 때 무엇을 반복하는가”라는 실제 사례로 시작한다. 기관 5명의 운영 부담은 관찰, 공통 문제·효과·구매는 가설로 분리한다.

다음 시연 묶음은 **한 업무의 지도 1장, 수정 린 캔버스 1장, 출처와 허용 범위를 확인한 집계 사례 또는 가상 건별 사례 1개, 선택한 업무용 화면 1~2개, 기준선 측정표**다. 개별 대기열과 학생용 공지 화면은 실제 선택한 업무에 필요할 때만 덧붙인다. 성공은 화면 수가 아니라 담당자가 한 건을 끝까지 처리하고 기존 방식과 시간을 비교할 수 있는지로 판단한다.

기존 [학생 우선 개선안](./project-improvement-roadmap.md), [학생 실험 실행 계획](./mvp-execution-plan.md), [학생 실험 상세 설계](./mvp-detailed-design.md)는 비교 기준과 구현 기록으로 유지한다. 기관 전환을 확정하면 학생 실험의 4/10 판정선을 기관 제품의 성과 목표와 혼동하지 않도록 발표·제출용 요약본에도 변경 시점과 이유를 표시한다.
