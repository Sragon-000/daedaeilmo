# 대대일모 기관 고객 전환 계획

작성일: 2026-10-13. 근거 범위는 1~6주차 최종 문서, 기관 인터뷰와 현재 구현이다. 이는 **다음 단계의 방향 제안**이다. 과거 학생 중심 실험이나 기관 유료 구매가 이미 검증된 것으로 해석하지 않는다.

## 결정할 고객과 문제

첫 고객은 **배재대학교에서 비교과·창업·학과 프로그램을 직접 운영하는 부서**로 좁힌다. 실사용자는 프로그램 담당자, 도입·예산 결정자는 부서 책임자 또는 예산 담당자, 학생은 기관이 제공하는 프로그램을 보는 이용자다. 실제 결재권자와 예산 경로는 아직 확인되지 않았다. 다른 대학과 외부 기관은 첫 파일럿 범위에서 제외한다.

잠정 문제는 “프로그램마다 신청·취소·확정·대기·참석 상태를 여러 도구에서 대조하며 반복 연락과 수작업을 한다”이다. 제품의 첫 약속은 **운영 상태와 다음 처리할 일을 한곳에서 확인해 담당자의 반복 작업을 줄인다**로 정한다. 모집 인원 증가, 신청 완료, 실제 참여 증가, 유료 구매는 별도 검증 결과다.

우선 후보 기능은 **신청 이후 확정·취소·대기자 충원 상태 관리**다. 기관 5명의 업무가 서로 달랐으므로 추가 확인에서 이 업무가 반복되지 않으면 같은 기관 고객 안에서 모집/홍보 또는 출석·수료 관리로 초점을 바꾼다. 고객을 고정하되 해결할 업무까지 성급히 확정하지 않는다.

## 제품의 중심 흐름과 재사용 범위

기관용 경로는 `프로그램 등록/공식 원문 검수 → 신청·취소·확정 현황 반영 → 처리 대기 확인 → 기존 채널에서 연락·처리 → 결과·작업 시간 기록 → 학생용 공지 갱신`으로 설계한다. 1차 파일럿은 학교 신청 시스템을 대체하지 않는다. 기관이 허용한 범위에서 **익명 상태표 또는 집계 CSV/수기 입력**을 쓰고 학생 연락처와 학번은 받지 않는다. 개별 상태가 필요하면 기관이 만든 가명 코드만 앱에 넣고 코드-실명 대응표는 기관 내부에 둔다. 실제 연락 발송과 출석 판정은 담당자의 기존 절차에 남긴다.

현재 코드는 학생 로그인·수동 시간표, 공식 공지 수집·검수, 행사 카드/원문 링크, 학생별 저장·원문 열기 **시도** 기록, 로그인 없는 시연 화면과 Mac 로컬 관리자 화면을 갖췄다. 공개 공지와 검수 기능은 학생에게 보여 주는 경로로 재사용할 수 있다. 반면 `campus_events`에는 기관 소유자·운영 단계·목표/신청/확정/참석/수료 수치가 없고 Mac 관리자 화면은 127.0.0.1 전용이다. 기관 담당자 제품으로 그대로 개방해서는 안 된다. 원문 클릭만으로 신청 또는 출석을 알 수도 없다.

| 유지·재사용 | 새로 필요 | 이번 범위에서 보류 |
| --- | --- | --- |
| 배재대 공개 공지, 원문·포스터, 검수 상태, 출처 변경 시 검수 해제, 학생용 공개 시연 | 기관/프로그램 소유권, 담당자 로그인·권한, 상태표, 반복 작업 대기열, 익명 CSV 입출력, 변경 이력, 작업 시간 측정 | 다른 대학 SSO, 학생 신청 대행·결제, 푸시 발송, 네이티브 앱, 리뷰·아바타 확장, OCR 확대 |

학생 앱은 유지하되 신규 개발 우선순위에서 내린다. 학생 화면은 기관이 등록·확인한 프로그램이 어떻게 보이는지 보여 주는 결과물이다. 공강 비교는 보조 기능이며 기관 가치의 핵심 지표가 아니다.

## 도입·수익 가설도 별도로 검증

초기 접점은 기존 기관 인터뷰 대상과 배재대 프로그램 운영 부서다. 첫 제안은 판매가 아니라 익명 자료로 진행하는 제한된 업무 파일럿이며, 기관 담당자의 사용 동의와 데이터 제공 허용 범위를 먼저 확인한다. 담당자가 편하다고 말하는 것과 부서가 비용을 지불하는 것은 다르므로, 결재권자에게 기존 도구 비용·외부 업체 검토 경험·보안 심사·예산 편성 시기·구매 단위를 묻는다. **실제 다음 단계 행동**인 추가 회의, 견적 요청, 파일럿 승인 또는 내부 검토 요청을 따로 기록한다. 가격은 그 전까지 정하지 않는다.

수익 후보는 기관의 프로그램 운영 지원비이지만 현재는 가설이다. 4~5주차 문서의 정보 관리 주 3시간·서버/알림 월 5만 원도 측정값이 아니다. 파일럿에서는 `프로그램당 수집·검수 시간 + 데이터 정리 시간 + 고객 지원 시간 + 호스팅 비용`을 기록해 실제 운영 원가를 계산한다. 기관이 절감한 시간만큼 팀의 수작업이 늘면 자동화/가격 구조를 다시 설계한다.

## 단계별 실행과 통과 조건

아래 수치는 **팀이 후속 조사 전에 정할 잠정 판정선**이며 일반적인 시장 기준이 아니다. 실제 프로그램 일정에 따라 단계 기간은 조정한다.

| 단계 | 결과물 | 통과 조건 |
| --- | --- | --- |
| A. 기관 문제 재확인 (약 1주) | 기존 기관 응답자 3명 이상 재접촉, 가능하면 다른 운영자 2명 추가. 최근 프로그램 하나의 익명 신청/취소/확정/출석 흐름, 사용 도구, 작업 빈도·시간, 누락·중복 사례, 결재권자 확인. 기관 캔버스와 기준표 1장. | 적어도 2개 운영 팀이 **같은 반복 업무**와 실제 사용 자료를 보여 주고 1개 팀이 파일럿 협의를 허용한다. 미달이면 화면 개발보다 기관 하위집단/문제 재선택이 먼저다. |
| B. 수동 지원 시연 (약 1주) | 학생 개인정보 없이 한 프로그램의 상태표와 처리 대기열 제작. 담당자는 기존 폼·시스템을 쓰고 팀이 익명 자료 정리·보고를 뒤에서 지원. 담당자 2명 이상이 자신의 업무를 따라가며 막힌 단계를 기록. | 담당자가 절약되는 단계와 도입 장벽을 모두 설명하고 기존 방식의 작업 시간을 측정할 수 있다. |
| C. 기관용 최소 제품 (약 2주) | 별도 기관 로그인/권한, 프로그램 등록·수정, 목표/신청/확정/취소/대기/참석/수료 상태, 변경 이력, 검수된 공지 발행, CSV 내보내기. 각 수치에 기준 시점과 고유 인원/회차 연인원 표시. B에서 확인된 경우에만 취소·대기 작업 대기열 구현. | 담당자가 자기 프로그램만 읽고 수정하며 타 기관·학생·비로그인 사용자는 접근 불가. 입력→수정→내보내기에 누락·중복이 없고 원본 대조 가능. |
| D. 실제 운영 파일럿 (프로그램 일정에 맞춰 2건 이상) | 승인받은 한 기관의 프로그램 2건 이상에서 기존 방식과 병행. 일별 작업 시간, 중복·누락, 상태 변경 소요 시간, 추가 입력 부담 기록. 원문 클릭은 별도 관심 지표로만 기록. | 잠정 목표: 반복 관리 시간 25% 이상 감소, 오류 증가 없음, 추가 입력 부담이 절감 시간을 넘지 않음. 담당자의 다음 회차 재사용 의사와 결재권자의 실제 검토 절차 확인. 2건은 학습용이지 일반화·유료 수요 확정 근거가 아니다. |

한 단계의 미달을 다른 지표로 덮지 않는다. 공통 업무가 없다면 비교과 전반 대신 창업·실습 등 과정이 비슷한 운영 팀으로 좁힌다. 시연이 작업을 늘리면 자동화보다 입력 절차부터 바꾼다. 도입 승인·데이터 제공이 없다면 실제 명단 없이 공개 자료와 익명 예제로만 시연한다.

## 기술·운영 선행 조건

1. 기존 학생 `members`와 기관 계정을 분리한다. `organizations`, `staff_memberships`, `programs`, `program_status_snapshots`, `program_actions`, `audit_log` 같은 구조를 검토하고 모든 기관 API에서 소속 기관·프로그램 범위를 확인한다. DB 변경 전 백업과 복구 시험을 한다.
2. 현재 Mac 관리자 토큰과 학생 포털 계정은 기관 직원 로그인에 재사용하지 않는다. 담당자 초대·권한 회수, 비밀번호 없는 로그인 또는 기관이 허용한 인증을 따로 설계한다. 기관 동의 없이 내부 데이터를 가져오지 않는다.
3. 현 Mac + 임시 Quick Tunnel은 화면 시연용으로 본다. 실제 업무 파일럿 전에 고정 주소, 장애 알림, 접근 권한, 백업/복구, 운영 책임자와 중단 절차를 마련한다. 기관 API를 현재 공개 프록시에 성급히 추가하지 않는다.
4. 원문 열기 **시도**, 신청, 확정, 참석, 수료는 서로 다른 수치다. 공식 연동이 없으면 신청 수는 기관이 준 집계/CSV의 기준 시각을 표시한다. 자동 추출·OCR은 확정 자료가 아니다.

첫 기관에서 작업 시간 절감과 반복 사용이 확인된 뒤에만 다른 부서로 복제한다. 다른 대학으로 확장할 때는 공지 구조·데이터 제공 범위·직원 인증을 학교마다 따로 확인한다. 배재대 학생 포털 로그인 구현만으로 다른 학교나 기관의 공식 연동을 약속하지 않는다.

## 문서와 발표 정리

역사 기록인 1~6주차 워크북의 당시 선택과 인터뷰를 새 방향에 맞춰 소급 수정하지 않는다. 새 린 캔버스에는 **기관 고객/담당자/결재권자**, 반복 업무, 기존 시트·폼·학교 시스템, 예상 절감 시간, 도입 장벽과 비용 가설을 적는다. 학생 `4/10 원문 이동`은 과거 B안 판정선으로 남기고 기관 파일럿 기준표를 별도로 만든다. 발표는 “학생이 공지를 못 찾는다”보다 “기관이 프로그램 운영 상태를 변경·대조할 때 무엇을 반복하는가”라는 실제 사례로 시작한다. 기관 5명의 운영 부담은 관찰, 공통 문제·효과·구매는 가설로 분리한다.

다음 시연 묶음은 **기관 업무 지도 1장, 수정 린 캔버스 1장, 익명 실제 사례 1개, 담당자용 두 화면(프로그램 현황·처리 대기), 학생에게 보이는 공식 공지 화면 1개, 파일럿 측정표**다. 성공은 화면 수가 아니라 담당자가 한 건을 끝까지 처리하고 기존 방식과 시간을 비교할 수 있는지로 판단한다.

기존 [학생 우선 개선안](./project-improvement-roadmap.md), [학생 실험 실행 계획](./mvp-execution-plan.md), [학생 실험 상세 설계](./mvp-detailed-design.md)는 비교 기준과 구현 기록으로 유지한다. 기관 전환을 확정하면 학생 실험의 4/10 판정선을 기관 제품의 성과 목표와 혼동하지 않도록 발표·제출용 요약본에도 변경 시점과 이유를 표시한다.
