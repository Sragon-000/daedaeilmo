# 대대일모 MVP 실험 상세 설계

작성일: 2026-10-12

상태: 핵심 경로 구현됨. 2026-10-12 공개 공지 11건 재수집·4건 검수 완료. 시간상 맞는 단일 행사 공급과 10명·2주 실험은 미완료.

상위 계획: [MVP 실험 실행 계획](./mvp-execution-plan.md)

## 1. 목표와 판정 범위

배재대 학생이 **자신의 가능한 요일·시간을 입력하고, 검수된 실제 행사 중 시간상 맞는 후보를 본 뒤, 별도 지시 없이 학교 원문으로 이동하는지** 검증한다. 이번 결과는 `프로토타입 + 오즈의 마법사` 방식의 학생 가치 검증이다. 학교 공지의 수집·검수는 운영자가 맡고, 학생은 모바일 웹에서 두 화면을 사용한다.

본 앱 `/`의 배재대 학교 인증, 회원·시간표·리뷰 기능은 그대로 유지한다. 실험 경로 `/experiment`는 **사전에 모집한 참여자의 개별 초대 링크**로만 열리며, 학교 비밀번호·학번·실명을 받지 않는다. 초대 링크는 재학생 인증 수단이 아니므로 참여자 자격은 모집 단계에서 사람이 확인한다. 링크가 유출되면 제3자가 공개 행사 목록을 볼 수 있다는 한계가 있다. 회원 데이터와 관리자 기능으로는 이동할 수 없어야 한다.

1차 지표는 2주 동안 참여 학생 10명 중 **시간상 맞는 검수 행사 카드에서 학교 원문을 자발적으로 실제 연 고유 학생 수**이다. 잠정 판정은 4명 이상이면 다음 반복 실험, 2명 이하이면 주요 원인 하나를 수정해 재시험, 3명이면 보류다. 10명 미완료, 행사 공급 부족, 접속 장애가 크면 성공·실패 판정 대신 관찰 결과를 보고한다. 클릭 시도만으로 실제 원문 열림·신청·참여를 주장하지 않는다.

## 2. 참여자 화면

| 단계 | 화면과 동작 | 실패·빈 상태 |
| --- | --- | --- |
| 초대 진입 | `https://<공개주소>/experiment#invite=<무작위 토큰>`을 연다. 브라우저가 주소의 토큰 조각을 즉시 제거하고 같은 출처의 접근 API에 전달한다. | 만료·회수·잘못된 링크는 행사 데이터를 주지 않고 운영자에게 새 링크를 요청하도록 안내한다. |
| 1. 가능한 시간 | 실험 목적·기록 범위·삭제 방법을 간단히 보여 주고 동의를 받는다. 요일 하나와 시작·종료 시간을 입력한다. 예: 수요일 13:00–17:00. | 동의하지 않으면 더 진행하지 않는다. 시작≥종료, 30분 미만, 허용 범위 밖은 제출할 수 없다. |
| 2. 행사 목록 | 앞으로 21일의 검수된 배재대 행사를 읽는다. `입력한 시간과 맞음`을 맨 위에, `일정 확인 필요`와 `다른 시간`을 아래에 구분한다. 카드에는 제목, 학교 출처, 행사 일시, 장소·대상·신청 정보, 최근 확인 시각, 학교 원문 버튼을 표시한다. 가능한 시간은 이 화면에서 고칠 수 있다. | 맞는 행사가 없으면 `현재 입력한 시간에 맞는 검수 행사가 없어요`라고 표시하고 다른 검수 행사는 볼 수 있게 한다. 검수 공급이 0건이면 운영상 공급 부족으로 기록한다. 서버 오류는 재시도와 안내를 표시한다. |
| 원문 보기 | 버튼은 사용자 동작으로 서버의 제한된 이동 경로에 `POST`한 뒤 배재대 공식 공지로 새 탭에서 이동한다. 원문 링크가 열렸는지 사용 후 관찰자가 별도로 확인한다. | 원문이 삭제되거나 이동에 실패하면 그 사실을 기록하고 원문 이동 성공으로 세지 않는다. |

모바일 기준 폭 320–430px에서 한 손 조작이 가능하도록 시간 입력과 원문 버튼을 크게 두고, `참여 가능`이나 `신청 가능`이라는 문구는 쓰지 않는다. 시간상 맞아도 대상 조건, 모집 현황, 장소 이동 시간은 학교 원문에서 확인해야 한다. 이용 가능한 시간은 정규 수업 시간표가 아닌 **참여자가 직접 적은 한 개의 주간 반복 구간**이다. 이는 기존 회원 시간표와 서로 동기화하지 않는다.

## 3. 데이터와 판정 규칙

### 공식 행사 공급

기존 `/api/events`는 학교 인증 후 배재대 공지 게시판을 수집해 `campus_events`에 저장한다. 같은 수집기를 Mac loopback 전용 `/api/experiment/refresh`에서도 운영자 비밀키로 호출할 수 있다. 운영자는 Mac 전용 관리자 화면에서 원문과 제목·행사일·시각·장소·대상·신청 정보·원문 URL을 대조해 `verified`로 지정한다. 첫 준비 단계에서 최근 후보 20건을 표본 검수하고 누락·오추출·중복·지난 행사·검수 시간을 기록한다. 이후 실험 기간에는 매일 수집을 갱신하고 변동된 후보를 다시 검수한다. 자동 배경 갱신은 없으므로 운영 절차에 `npm run experiment:refresh`를 포함한다. 2026-10-12에는 후보 11건만 수집되어 목표 표본 20건을 채우지 못했다.

실험 목록 API는 수집 작업을 수행하지 않는다. `campus_events`에서 `school='pcu' AND review_status='verified'`인 행만 읽고, `last_seen_at`이 24시간 이내이며 앞으로 21일에 열릴 행사를 기본 목록으로 둔다. 날짜·시각이 불분명한 공지는 게시일이 최근 120일 이내이고 운영자의 검수 시각이 7일 이내인 경우에만 `일정 확인 필요` 구역에 놓는다. 지난 행사나 확실히 지난 신청 마감일이 있는 행사는 숨긴다. 24시간 이상 갱신되지 않으면 최신 정보라고 주장하지 않고 공급 부족/갱신 필요 상태를 표시한다. 응답의 `supplyStatus`는 `ready`(표시할 행 있음), `empty`(표시할 행 없음), `stale`(갱신 지연)로 고정한다. **원문 `source_hash`가 바뀌면 기존 코드가 검수를 `unreviewed`로 되돌리므로 실험 API에서도 즉시 빠져야 한다.** 검수 전·숨김·학교 외 URL과 운영자가 원문 접근 불가를 확인한 행은 공개하지 않는다. 수집 실패 직후 과거에 검수한 행이 최대 24시간 남을 수 있으므로, 실패를 발견한 운영자는 해당 행을 바로 숨기고 장애를 기록한다.

응답은 `id`, `title`, `category`, `date`, `start`, `end`, `schedule`, `place`, `audience`, `application`, `deadline`, `officialUrl`, 허용된 `posterUrl`, `reviewedAt`, `lastSeenAt`, `fit`만 명시적으로 구성한다. `payload`, OCR 증거, 회원 필드, 운영자 메모는 보내지 않는다. 포스터는 `https://www.pcu.ac.kr/upload/`의 허용된 이미지 URL일 때만 표시하고 실패하면 텍스트 카드로 계속 동작한다. 원문 URL은 `https://www.pcu.ac.kr/kor/article/(Notify_1|Event_1)/<숫자>` 형식만 허용한다.

### 가능한 시간 계산

서버와 UI가 공유하는 순수 함수 `assessAvailableWindow(event, window, now)`를 새로 둔다. 기존 `assessEvent()`는 **등록 수업과 행사 충돌을 계산**하므로 공강 구간에 그대로 적용하면 빈 수업 목록을 `시간표 입력 필요`로 판단한다. 날짜 유효성·마감 확인 아이디어는 재사용하되 판정 함수는 분리한다.

- `window`: 월=0 … 일=6, 시작·종료는 한국시간 00:00부터의 분. 입력은 08:00–22:00, 길이 30분–8시간의 한 구간으로 제한한다.
- 행사 날짜와 시작·종료가 모두 검수되어 있고, 행사 시작이 현재보다 미래이며, 행사 날짜의 한국 요일이 입력 요일과 같아야 시간 비교를 한다.
- 행사 전체가 가능한 구간 안에 **전후 각 10분의 이동 여유**와 함께 들어갈 때만 `time_match`다. 즉 `event.start >= window.start + 10`이고 `event.end <= window.end - 10`이다.
- 날짜·시각·마감이 모호하면 `schedule_unknown`; 요일 또는 시간이 다르면 `different_time`; 종료·마감이 확인되면 `closed`로 분류한다. `closed`는 목록에서 제외한다. 운영자가 원문을 대조해 `단일 일시` 유형을 지정해야만 `time_match`가 가능하다. `여러 회차 과정`과 `기간 중 참여`는 단일 일시로 취급하지 않고, 기간형 활동은 별도 구역에 표시한다. 운영자가 참여 종료일을 확인한 경우 그 다음 날부터 목록에서 제외한다.
- 모든 날짜 경계와 요일 계산은 `Asia/Seoul`을 사용한다. 마감이 날짜만 적힌 경우 그날 중 정확한 마감 시각을 추측하지 않고 원문 확인 안내를 붙인다.

예: 수요일 13:00–17:00을 입력했고 수요일 행사 14:00–16:00이면 `time_match`다. 12:50–15:00이면 시작이 구간 밖이므로 `different_time`이다. 시각이 없는 포스터만 확인된 행사는 `schedule_unknown`이며 `time_match`로 올리지 않는다.

## 4. 경로와 API 계약

| 경로 | 입력·성공 결과 | 접근 조건 |
| --- | --- | --- |
| `GET /experiment` | 두 화면 앱 셸. 토큰은 URL의 `#invite` 조각에만 있고 첫 렌더 후 `history.replaceState`로 제거한다. | 공개 셸만 반환; 행사 데이터 없음. |
| `POST /api/experiment/access` | `{token}` → `204`, `experiment_session` 쿠키 발급. 원문 토큰은 저장하지 않고 SHA-256 해시로 조회한다. | 같은 출처 요청, 길이 제한, 유효·미회수 초대, 시도 횟수 제한. |
| `POST /api/experiment/consent` | `{agreed:true}` → `204`, 동의 시각 저장. | 유효한 실험 세션. 철회는 운영자에게 요청할 수 있게 안내. |
| `POST /api/experiment/availability` | `{day,start,end}` → `200`과 판정 기준 버전; 해당 참가자의 입력 구간을 저장하고 `availability_submitted` 기록. 재입력 가능. | 동의한 실험 세션, 같은 출처, 엄격한 범위 검사. |
| `GET /api/experiment/events` | `{items, asOf, supplyStatus, fitRuleVersion}`. 서버가 저장된 구간으로 각 행의 `fit` 계산. | 동의·입력 완료한 실험 세션. 인증된 DB 행에서 허용 필드만 제공. |
| `POST /api/experiment/actions` | `{action:'feed_viewed'|'supply_empty'}` → `204`. 실제 화면 렌더 뒤 호출. | 동의·입력 완료한 실험 세션, 같은 출처. 임의 이벤트 ID·개인정보는 받지 않음. |
| `POST /api/experiment/exit` | `204`, 실험 세션 쿠키 삭제. | 같은 출처 요청. 화면의 `체험 종료`에서 사용. |
| `POST /experiment/out` | 사용자 클릭으로 연 `target="_blank"` 폼의 `eventId`를 받는다. DB에서 검수 상태와 허용 URL을 다시 확인하고 당시 `fit`·`source_hash`와 이동 시도를 기록한 뒤 공식 공지로 `303` 이동. | 유효한 세션, 동의·입력 완료, 같은 출처 요청, 현재도 공개 가능한 행사. 외부 URL 파라미터를 받지 않음. |

오류 규약은 잘못된 입력 `400`, 세션 없음/만료 `401`, 동의 전 `403`, 초대 만료·회수 또는 행사 공개 중단 `410`, 서버·DB 장애 `503`, 과다 요청 `429`로 한다. 모든 실험 응답은 `Cache-Control: no-store`, 실험 경로는 `Referrer-Policy: no-referrer`를 사용한다. `experiment_session`은 별도 서명 비밀로 보호되는 `HttpOnly; Secure; SameSite=Lax; Path=/` 쿠키이며 초대 만료보다 길지 않게 발급한다. 서명된 내용은 초대 ID·세션 버전·만료 시각만 담는다. 서버는 매 요청마다 DB에서 초대의 만료·회수·세션 버전을 재확인하므로 토큰 재발급으로 종전 세션도 무효화할 수 있다. 체험 종료 시 쿠키를 삭제한다.

토큰 조각 방식은 토큰이 최초 GET URL·서버 접근 로그·원문으로 전달되는 것을 줄인다. 클라이언트 메모리에는 접근 API 응답 전까지 잠시 남으므로, 실험 화면에 제3자 스크립트나 추적기를 넣지 않는다. 서버 측 `Origin` 검사는 변조된 요청을 막는 보조 수단이며 초대 자체의 소유자를 증명하지 않는다. 원문 이동은 조회(`GET`)로 기록하지 않아 브라우저 사전 로드나 외부 사이트의 링크 요청이 클릭으로 집계되지 않게 한다.

## 5. 저장 구조와 기록

기존 `members`, `member_courses`, `member_reviews`와 외래키를 잇지 않는다. 다음 두 테이블을 Drizzle 스키마에 추가하고 신규 마이그레이션으로 반영한다. 운영자는 마이그레이션 전에 Mac 관리자 백업을 실행한다.

| 테이블 | 주요 열 | 목적 |
| --- | --- | --- |
| `experiment_invites` | `id` UUID PK, `participant_code` UNIQUE(`U01`…), `token_hash` UNIQUE, `session_version`, `created_at`, `expires_at`, `revoked_at` nullable, `consented_at` nullable, `available_day/start/end` nullable, `availability_updated_at` nullable | 초대·동의·한 개의 공강 구간 관리. 재발급 시 버전 증가. 실명·학번·비밀번호 없음. |
| `experiment_actions` | `id` UUID PK, `invite_id` FK, `action`, `event_id` nullable, `fit_at_action` nullable, `source_hash_at_action` nullable, `created_at` | 동의 후 이용 단계와 원문 이동 **시도** 기록. `invite_id,action,created_at` 인덱스. IP·기기 식별자·원문 토큰 저장 없음. |

참여자 코드별 초대 링크는 Mac 로컬 관리 명령에서 128비트 이상 난수로 만들고, DB에는 해시만 저장한다. 생성 직후 운영자에게 한 번만 링크를 보여 준다. 기존 공개 관리자 화면에 초대 생성이나 개인별 기록을 노출하지 않는다. 링크 분실 시 토큰을 재발급하고 이전 토큰·세션을 무효화한다. 한 링크를 여러 사람이 공유하면 앱만으로 구별할 수 없으므로 관찰 기록에 표시하고 해당 사례를 판정에서 검토한다.

원문 클릭의 서버 기록은 `original_open_attempt`이다. 실제 학교 페이지가 로드된 증거는 관찰자가 `participant_code`, 시각, 원문 행사 ID, 열림 여부, 실패 이유를 별도 로컬 실험 시트에 기록한다. 실명 대응표가 꼭 필요하면 앱 DB 밖에 두고 접근자를 제한한다. 1차 지표 계산은 **동의·입력·목록 노출을 완료한 초대 코드 중 `fit_at_action='time_match'`인 원문 시도가 있고 실제 열림이 확인된 코드의 수**다. 분모 10명은 모집한 전체 참여자로 별도 기록해 중도 이탈을 빠뜨리지 않는다. 동일 코드의 반복 클릭은 1명으로 센다. 보조 지표는 목록 노출자 수, 시간상 맞는 행사 공급률, 모든 원문 클릭, 링크 실패, 운영자 검수 시간이다.

실험 종료 후 결과 검토를 마치면 초대·공강·행동 로그 및 별도 관찰 시트는 30일 안에 삭제하고, 개인별 식별이 없는 합계만 남긴다. 참여 철회 시 해당 초대를 회수하고 관련 기록을 삭제한다. 실제 보존 기간과 연락 창구는 첫 화면의 동의 문구에 동일하게 표시한다.

## 6. 호스팅·보안·운영

`scripts/hosting/public-proxy.mjs`의 공개 허용 목록에 `/experiment`, `/experiment/out`, `/api/experiment/access|consent|availability|events|actions|exit`만 정확히 추가한다. `/api/admin`, Mac 관리자 포트 4320, 회원 API의 인증 요구는 유지한다. 현재 프록시의 Host·HTTPS·Origin 검사, 요청 수 제한을 실험 API에도 적용하고, `access`에는 로그인 수준의 별도 속도 제한을 둔다. 프록시가 현재 모든 응답에 `Referrer-Policy: same-origin`을 덧씌우므로 **실험 경로에만 `no-referrer`가 최종 응답에 남도록** 수정해야 한다. 새 탭으로 보내는 원문 이동 폼에도 `rel="noopener noreferrer"`를 적용한다.

Mac 호스팅은 현재 실행기에서 시작·상태 확인·중지가 가능하지만 공개 모드는 `trycloudflare.com` 임시 주소를 발급한다. 2주 동안 재방문을 측정하려면 고정 도메인/터널을 준비하거나, 주소 변경 시 참여자별 토큰을 재발급하고 새 링크를 전달하는 절차를 정한다. 토큰을 DB에 해시로만 저장하므로 생성된 원문 링크를 별도로 보관하지 않으면 주소만 바꿔 재전송할 수 없다. 서버 중단 시간, 공지 수집 실패, 검수 후보 수를 일별 운영 기록에 남긴다. Mac 절전·네트워크 이탈·터널 중단을 실제 폰에서 점검한다.

매일 운영 순서는 `Mac 서버/HTTPS 상태 확인 → 학교 공지 수집 갱신 → 변경된 행 검수 → 실험 경로에서 노출·원문 확인 → 후보 수와 작업 시간 기록`이다. 비정상 행은 `hidden` 처리하거나 정정 후 검수한다. 학생 실험 중 후보가 0건인 날은 제품 선호도 실패가 아닌 공급 문제로 구분한다.

## 7. 구현 순서와 검수 기준

예상 수정 위치는 `app/experiment/page.tsx`(두 화면), `app/experiment/out/route.ts`(안전한 원문 이동), `app/api/experiment/*`(초대·동의·입력·목록·기록·종료), `lib/experiment-session.ts`(서명·검증), `lib/experiment-fit.ts`(순수 시간 판정), `lib/experiment-catalog.ts`(검수 행과 허용 필드), `db/schema.ts` 및 신규 Drizzle 마이그레이션, `scripts/experiment/invites.py`(Mac 로컬 초대 관리), `scripts/hosting/public-proxy.mjs`(허용 경로·헤더)다. 기존 회원 인증 API의 접근 조건은 수정하지 않는다.

1. **행사 공급:** 후보 20건 원문 대조표 작성, 검수된 행만 읽는 조회 함수와 허용 필드 DTO 구현. 원문 변경 시 실험 목록에서 자동 제외되는지 확인.
2. **실험 접근:** 스키마·마이그레이션, 초대 생성·회수 로컬 명령, 토큰 교환·쿠키 검증 구현. 무효·만료·회수 링크와 초대 없이 회원 데이터 접근 불가를 확인.
3. **화면·판정:** 2화면 모바일 흐름, 가능한 시간 입력, `assessAvailableWindow` 구현. 날짜·요일·시간 경계, 10분 여유, 모호한 일정, 신청 마감, 한국시간 자정 주변을 테스트.
4. **측정·운영:** 원문 이동 기록·공식 URL 리다이렉트, 실험 집계·철회 절차, 공개 프록시 허용 목록과 보안 헤더 수정. iOS Safari·Android Chrome에서 다른 Wi-Fi와 이동통신망으로 전 과정 확인.
5. **실험 시작 판정:** 모집자 10명에게 개별 링크를 발급하기 전, 검수 행사 공급·모바일 접속·실제 원문 열림·기록 집계가 모두 동작하는지 팀 밖 테스트 폰으로 확인. 그 뒤 2주 사용 실험을 시작.

단위 검증은 공강 판정의 순수 함수에 집중한다. 통합 검증은 `verified`만 공개되는지, 원문 변경·회수·만료가 즉시 반영되는지, 학교 계정 없는 초대 세션이 `/api/profile`, `/api/timetable`, `/api/reviews`, `/api/event-saves`, `/api/event-opens`를 사용하지 못하는지, 공개 프록시가 Mac 관리 API를 거부하는지를 확인한다. 클릭 기록과 수동 실제 열림 기록을 구분해 집계하는 시험 사례를 한 명의 중복 클릭으로 검증한다.

## 8. 설계상 한계와 이후 결정

- 초대 기반 실험은 접근 범위를 좁히지만 **재학생 증명은 하지 않는다**. 정식 앱의 학교 인증을 대체하는 구조로 확대하지 않는다.
- 임시 터널 주소와 수동 검수에 의존하므로 공급·가동률과 운영 시간이 결과 해석에 포함된다. 행사 데이터가 적으면 화면만 바꿔도 가치 가설을 검증할 수 없다.
- OCR은 후보를 찾는 보조 수단이다. 일시·대상·신청 마감을 원문 대조 없이 자동 확정하지 않는다.
- 계명대 연결, 네이티브 iOS·Android 앱, 공간 리뷰, 알림, 신청 대행은 이번 1차 지표의 필수 요소가 아니다. 학생 원문 이동과 운영 가능성이 확인된 뒤 별도 우선순위로 다룬다.
